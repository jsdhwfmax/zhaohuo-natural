# 当前版本适配

v2.0.0 多角色运行时已完成编译、52 项配置解析回归、78 项纯策略测试、静态接口检查及 16 项离线兼容测试。新 DLL 在 Steam build `25957922` / `release_1.0.6000.2` 的六套赵活外观及全部原版模式共七次真实游戏诊断通过，包含两位 NPC、头像、身份负例与批量加载；38 张新增外观诊断图已人工审阅。普通 Steam 启动进入主菜单，持续响应 92.3 秒，插件日志无错误。对应记录见 [v2 实机验收](../verification/character-runtime.json)。范围为隔离的真实资源与 UI 组件，不涉及推进剧情或读写存档。

下文保留 v1.x 的背景：旧版已验证 Steam build `25953419` / `release_1.0.6000.0` 与“崆峒神威”热更新 build `25957922` / `release_1.0.6000.2`，运行环境为 Unity `2020.3.49f1`、Windows x64 Mono。旧构建的历史报告不能替代 v2 新 DLL 的实机结论。当前剧情角色通过协程和 Addressables 按需加载表情，创建角色后只遍历一次图片不能覆盖后续资源。

## 立绘加载

插件用 Harmony 包装 `StoryCharacterController.LoadPortrait` 和 `LoadPortraitAssetByAddressable` 返回的协程，在原加载完成后执行替换；同步 `LoadPortraitSync` 通过 Postfix 处理。同时更新 Portraits 与游戏创建的 UI Image，原 Addressables 资源生命周期交给游戏管理。

新图生成 FullRect Sprite，保留原 pivot 与等效 pixels-per-unit。`portrait-layout.tsv` 记录原画布与人物边界。加载时按 alpha>16 检测新图边界，并预留 2 像素边缘，等比缩放到对应布局，避免 PNG 留白差异造成位置漂移；纹理和 Sprite 缓存避免每次对白重复读取。

v2 范围为赵活原 47 张成人表情，以及唐布衣、夏侯兰基础成人资源与已核验复用同一资源的成人别名。匹配同时要求精确游戏 Id、对象名、实际 Addressables canonical 路径和加载 handle 对应的 Sprite 实例。少年 NPC、所有独立幼年、蒙面、魂、分割特殊形态和其他角色保持原画；赵活旧版已覆盖的少年 normal 因确证复用成人图而保留。缺图或 NPC 缺合法布局时回退原画。

赵活继续用原 `Portraits`、`portrait-map.txt` 和 `portrait-layout.tsv`。NPC 分别读取 `Characters/tang-buyi/Portraits`、`Characters/xiahou-lan/Portraits` 与各目录的 `portrait-layout.tsv`，不按相同表情名跨角色查找。同步 hook 在 Prefix 快照原加载 handles、Postfix 核对新增来源；协程在实际迭代开始与结束时执行相同判定。缓存命中无新增 handle，保留既有替换；存在并发或来源歧义时保留原画。

## 独立面板

属性面板 `PlayerAvatarPanel.OnEnable` 有两个 normal 分支，两者使用新常态图。人物关系面板 `SocialStatPanel.UpdateInfo` 和角色介绍 `CharacterIntroPanel.TransitionAvatar` 也有针对主角的钩子；NPC 保持原逻辑。

## 实际验证与边界

两个已实测构建均在实际游戏进程中独立创建 `StoryCharacterController`，调用真实 Setup、同步/异步加载、Addressables 与游戏 UI Image。50 个成人资源全部加载，47 个新图替换，back 与两张 shadow 保留原作；缓存、UI 引用及非主角保护通过。实际 `PlayerAvatarPanel.OnEnable` 两个天赋分支也通过。新构建证据见[验证目录](../verification/runtime-build25957922/README.md)。

资源诊断不推进剧情或读写存档。它证明加载与显示链路可用，不代表通关所有剧情，也没有逐一操作人物关系与角色介绍界面的完整交互。两个构建另外均通过普通无测试参数的 Steam 启动，确认插件加载和窗口响应；新构建连续观察约 81 秒。公开 PASS 属于资源诊断，普通启动记录另行保留，不公开个人日志。

通过 Steam 启动游戏；游戏自带的 Steam 检查可能在直接运行 Mortal.exe 时请求重新启动。插件没有绕过此检查。普通模式没有退出游戏逻辑，自测退出只在显式传入两个诊断参数时执行。

## 游戏更新与离线检查

安装器的 `SupportedGameBuilds` 保存已实机验证构建的完整指纹组，逐组核对 Assembly-CSharp、Mortal.Core、Mortal.Story 和 Fungus 四个程序集 SHA-256，不将各 DLL 的可接受哈希拆成独立列表。只有 Steam 清单 build 与该完整组同时匹配时，结果才采用 `VerifiedFingerprint`；此时 `MatchedBuildId` 对应已验证构建。

新 build、缺少 Steam 清单，或未命中完整指纹组时，v1.0.2 调用 `installer/CompatibilityProbe.ps1` 执行离线检查。即使四个 DLL 与旧组相同，只要 Steam build 不匹配，也必须检查资源，防止遗漏仅改变资源包的更新。成功结果为 `OfflineCompatibilityProbe`，`MatchedBuildId` 保持为空，不能据此声称新构建已经实机验证。

探针使用随包固定版本 Mono.Cecil 读取元数据、方法实现和依赖引用，结合 `installer/compatibility-baseline.json` 核对资源与框架文件。游戏程序集不加载为可执行代码，不被改写。基线与工具文件缺失、指纹不符、解析失败、关键方法或资源变化时均不放行。

资源与运行库策略保持保守：395 个固定文件约 2.30 GB，包括 130 个 Managed 依赖、190 个完整 Addressables bundles、2 个 catalog/settings、51 个场景或序列化资产、20 个 Mono 运行库或配置、`Mortal.exe` 与 `UnityPlayer.dll`。`globalgamemanagers` 单独规范化唯一可见 release 版本文本，其余内容须一致。

v1.x 的 `Mortal.Core` 检查范围包含 147 个立绘依赖方法（含协程状态机与传递辅助调用）、35 个类型布局和旧插件的 19 个游戏成员引用。v2 新 DLL 使用 23 个游戏成员引用，已更新插件 hash、引用计数和基线 pin，并通过 [16 项离线兼容检查](../verification/character-manager-compatibility.json)。395 个固定文件的内容边界逐项未变，新增反射字段 `_operationList` 位于既有整体 hash 固定的 Mortal.Story.dll 中。NPC bundles 已在原固定资源全集中，不能为放行更新而删除资源校验。

该策略主要放行资源、运行库及相关实现结构未变的部分代码热修复，剧情或资源更新可能被保守拒绝。历史探针在 PowerShell 5.1 下通过 [12 项专项检查](../verification/compatibility-probe-tests.json)，包括实际游戏只读扫描及独立副本中的实现、资源和工具变异测试；历史安装器有 [74 项模拟集成回归](../verification/installer-tests.json)。这些证据不混作未来构建或新 DLL 的实机验证。

build `25957922` 的 Mortal.Core 指纹为 `E2FE344EA90DED6E11F06711DE86F27290E005D817B21755149F9EE24966FC9F`，其余三个受检 DLL 与旧构建相同。相关立绘接口、实现与字段经比较保持兼容，并已重新运行实际资源诊断。未对中间 build `25956595` 作实际游戏验证；不会把未知构建的静态检查结果补写成这类历史实测。

更新基线仍需重新检查方法签名、加载时序、资源与布局，并实际运行诊断，不能仅移除版本检查。插件本身不会阻止 Steam 更新；已有公开旧包在载荷未变时可由 v1.0.2 直接重新检查。用户需保留完整外部包并主动运行检查入口，不能依赖普通游戏启动触发它。
